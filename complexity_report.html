Unnecessary Complexity in Offline Storage

Analyzed crates/openre-cli/src/context.rs (OfflineStore implementation) and related CLI commands.

1. Redundant Project Store

File: crates/openre-cli/src/context.rs · Lines 78-81, 102-116

Summary: OfflineStore embeds a ProjectStore (line 79) AND creates a separate projects table in meta_conn (lines 102-116). Both store project metadata with overlapping fields.

Simpler form: Use only the meta_conn projects table, or only ProjectStore — not both.

Failure scenario: Data divergence: create_project writes to meta_conn but ProjectStore has its own project_id (line 180) that never gets used. Two sources of truth for "what projects exist" → sync bugs, double storage.

2. Copy-Paste CRUD Methods

File: crates/openre-cli/src/context.rs · Lines 209-422 (projects), 427-684 (scans), 715-911 (analysis_jobs)

Summary: Three near-identical CRUD blocks (~700 lines total): create/list/get/update/delete/count for projects, scans, and analysis_jobs. Only table names and column lists differ.

Simpler form: A single generic Repository<T> trait with table_name, columns, from_row, to_params associated items. Or a macro generating the boilerplate.

Failure scenario: Bug fix in one (e.g., date parsing) must be manually copied to three places. Currently list_projects has search but list_scans has status_filter — inconsistent capabilities drift over time.

3. Deep Nesting in Dynamic UPDATE

File: crates/openre-cli/src/context.rs · Lines 336-395, 580-654, 786-860

Summary: update_project/update_scan/update_analysis_job each build dynamic SQL with Vec<Box<dyn ToSql>>, manual param ref conversion, existence check, early returns — 60+ lines each.

Simpler form: Use rusqlite::named_params! or a small helper: update_row(table, id, fields: &[(&str, &dyn ToSql)]). Or accept a closure: conn.execute_update("UPDATE ... SET ? WHERE id = ?", params).

Failure scenario: Param order mismatch between updates vec and params_vec → silent wrong-column update. The Box<dyn ToSql> erases type info so compiler can't catch it.

4. Redundant Fields in OfflineAnalysisJob

File: crates/openre-cli/src/context.rs · Lines 59-75

Summary: OfflineAnalysisJob has both stages: Vec<String> (line 70) AND total_stages: u32 (line 68). total_stages == stages.len() always.

Simpler form: Drop total_stages; derive via .len(). Or drop stages if only count matters (but stages carries names for display).

Failure scenario: Code creates job with stages: vec!["a", "b"] but total_stages: 5 → UI shows "2/5 stages" incorrectly. No validation enforces consistency.

5. String Status Fields Instead of Enums

File: crates/openre-cli/src/context.rs · Lines 26-75

Summary: OfflineProject.is_public: bool (ok), but OfflineScan.status: String (line 46) and OfflineAnalysisJob.status: String (line 64) are free-form strings. Values like "pending"/"running"/"completed"/"failed"/"cancelled" scattered across CLI commands.

Simpler form: enum ScanStatus { Pending, Running, Completed, Failed, Cancelled } with serde(rename_all = "lowercase"). Same for JobStatus.

Failure scenario: Typo in CLI: status: "runing".to_string() → stored, displayed, but filter WHERE status = 'running' misses it. No compile-time check.

6. Manual Connection Take/Put Pattern

File: crates/openre-cli/src/context.rs · Lines 195-206

Summary: Every DB method calls take_meta_conn().await?, does work, then put_meta_conn(conn).await. If any early return / ? / panic skips put, connection leaks (mutex stays empty → next caller gets "already in use" error).

Simpler form: Scoped guard: let _guard = MetaConnGuard::new(&self.meta_conn).await; with Drop impl that puts back. Or with_conn(|conn| async { ... }).await pattern.

Failure scenario: update_scan at line 637 does self.put_meta_conn(conn).await; then self.get_scan(id).await which calls take_meta_conn again — but if get_scan errors before its put, the conn is leaked. Two sequential take/put pairs instead of one scope.

7. Repeated DateTime Parse Boilerplate

File: crates/openre-cli/src/context.rs · Lines 260, 286, 321, 490, 523, 564, 769, 798, 896, 899

Summary: chrono::DateTime::parse_from_rfc3339(&row.get::<_, String>(?)?)?.unwrap().with_timezone(&chrono::Utc) repeated 10+ times across all from_row closures.

Simpler form: Helper: fn parse_utc(s: &str) -> DateTime<Utc> { DateTime::parse_from_rfc3339(s).unwrap().with_timezone(&Utc) } or implement FromSql for a wrapper type.

Failure scenario: Schema changes to store timestamps as INTEGER (unix epoch) → 10+ sites to update. Also .unwrap() panics on malformed data instead of returning error.

8. Box for Dynamic UPDATE Params

File: crates/openre-cli/src/context.rs · Lines 360, 607, 813

Summary: Dynamic UPDATE uses Vec<Box<dyn rusqlite::ToSql>> then converts to Vec<&dyn ToSql> for execute. Heap allocation + dynamic dispatch for 3-7 simple params.

Simpler form: rusqlite::params![&val1, &val2, ...] with optional fields as Option<&dyn ToSql> handled by params_from_iter or a small macro. Or build SQL with named params: UPDATE ... SET name = :name WHERE id = :id + named_params! { :name:&name, :id:&id }.

Failure scenario: Param order mismatch (see #3). Also allocation overhead on every update call — measurable in tight loops (e.g., scan progress updates every second).
